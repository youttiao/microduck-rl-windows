# 把人体动作库迁到 MicroDuck

> 目标：找一个标准的人体动作库 → 映射到鸭子 → 一个动作训一个策略 → 堆起来当技能库。

这套东西**上游已经有一大半**，但没合并到 `develop`，而且**没有任何人体动作库的导入器** —— 那正是缺的那块。这份文档说明现状、本仓库补了什么、以及怎么用。

## 一、上游已经有的（但没合并）

`pollen-robotics/microduck_rl` 有两个**未合并**的分支带着完整的动作跟踪环境：

| 分支 | 日期 | 内容 |
|---|---|---|
| `expressive-motions` | 2026-10-30 | 表达性动作环境 + 4 个参考动作（`tremendous_planted/v3/v3_bold/v4.csv`） |

```
（每个还有 -R2- 变体：从零训而不是从走路策略热启动）
```

### 关键设计：策略不数拍子，相位走指令通道

上游 `AGENTS.md` 说得很硬：

> 早期版本让策略自己数着拍子做坐下-站起，**十次全挂** —— PPO 的探索噪声几秒内就把关节里的时钟冲垮了。

上游的解法：**把相位 φ = t/T 塞进指令通道**。

```
指令 = [cos(2πφ), sin(2πφ), 0]     ← twist 的两个槽位
```

于是策略知道"现在到动作的第几点了"，但**不需要自己计时**。真机上 `robotd` 每个控制周期按同样的方式驱动 φ。这和 `ground_pick` 用的是同一套机制。

**这直接决定了观测布局不用改**：61 维观测里，`twist` 的 3 个槽位被相位占用，`head`/`body` 的 10 个槽位置零。其余 48 维本体感知不变。所以**训出来的策略和走路/站立策略可以热切换**，真机的运行时不用改。

### 目标格式："Tremendous" 通道

上游自己定义的一种人体动作参考格式（`tasks/expressive_motions.py`）。**8 个通道**，全部是"相对站立姿态的偏移"：

| 通道 | 含义 | 范围 |
|---|---|---|
| `roll` | 躯干滚转（ZYX Euler 的 roll） | |
| `pitch` | 躯干俯仰（>0 = 低头） | |
| `yaw` | 躯干偏航（相对动作起始朝向） | |
| `dz` | 躯干高度偏移（米） | 向上 ~+3mm，向下 ~-15mm |
| `neck_pitch` | 脖子俯仰（>0 = 头抬高） | HOME 0.349, [-1.571, 1.047] |
| `head_pitch` | 头部俯仰（>0 = 低头） | HOME 0.349, [-1.571, 1.571] |
| `head_yaw` | 头部偏航（>0 = 看左） | HOME 0, ±2.967 |
| `head_roll` | 头部侧倾 | HOME 0, ±0.436 |

CSV 格式：`t` + 8 个值 + 8 个导数，50 Hz。

## 二、缺的那块：人体动作 → Tremendous 通道

**上游、mjlab、社区里都没有任何人体动作库的导入器。** 上游的"Tremendous"动作是**手写的**（内部 `notes/dodge/tools/` 里的脚本生成），一个一个调出来的。

本仓库补上这个：

```
tools/
├── retarget_human.py        # 人体关节位置 → Tremendous CSV
├── duck_head_ik.py          # 头部姿态 → 4 个关节角（对着真 MJCF 数值求解）
├── make_motion_library.py   # 批量：目录 → 一堆 CSV + 注册片段
└── test_retarget.py         # 地面真值测试（不需要任何数据集）
```

### 为什么用"关节位置"而不是 SMPL 参数

表达性动作只需要人体三样东西：**躯干朝向、躯干高度、头部朝向**。这三样**从关节位置就能读出来**，所以根本不需要 SMPL/SMPL-X 身体模型。

两个好处：
- **绕开了 SMPL-X 的许可**（见第五节）
- **任何给 3D 关节位置的数据集都能当输入**，不用转格式

### 头部映射：用真机器人数值求解，不手推

鸭子的脖子是四个铰链：`neck_pitch` / `head_pitch` / `head_yaw` / `head_roll`。它们的轴在自己的 body 局部系里都是 `0 0 1`，而 `neck_pitch` 这个 body 装了 180°，所以**关节不是简单欧拉链**：

- `neck_pitch > 0` = 头往后仰
- `head_pitch > 0` = 下巴往下点

**符号是相反的。** 手写复合公式很容易搞错，而且错了很难发现。

所以本仓库的做法是：**建真模型，数值求解**。

- 头部的"朝向系"取 `head_camera` site（x=前，y=左，z=上）—— 这就是机器人真正的"看向哪"
- 求解器：阻尼最小二乘，误差 = 目标姿态与实际姿态的测地角
- 雅可比就是四个关节在世界系里的轴（铰链链上，site 的角速度等于 body 的角速度）
- 每个解约 **6 ms**，一个 15 秒的动作（750 帧）不到 5 秒

**实测精度**：小幅度头部运动（真实重定向会遇到的量级）平均残差 **0.43°**、最大 18°（那是撞到 `head_roll` ±25° 的硬限位）。

验证过的符号（与上游 `expressive_motions.py` 的文档逐条一致）：

```
neck_pitch +0.30  →  看方向上抬 +0.296   （头抬高 ✓）
head_pitch +0.30  →  看方向下压 -0.296   （下巴下点 ✓）
head_yaw   +0.30  →  看方向侧移 +0.296   （往左看 ✓）
head_roll  ±0.30  →  看方向不变          （绕自身轴滚 ✓）
```

### 躯干朝向：注意两件事

1. **上轴要从脖子取，不能从头取。** 头是相对躯干动的，用头关节位置算躯干的"上"方向，会被每一次点头污染。
2. **躯干的 roll/pitch 是绝对量，yaw 是相对量。** 环境里 `_ex_state` 量的是：
   ```python
   yaw = atan2(sin(rpy_yaw − yaw0), cos(rpy_yaw − yaw0))   # 相对起始
   dz  = root_z − mean_foot_z − STAND_HEIGHT              # 绝对
   head = (servo_joint_pos − servo_default_joint_pos)      # 相对 HOME
   ```
   所以重定向的参考也必须照这个来：roll/pitch 要加上鸭子自己的站立姿态基准（本机测出来是 0.00° / −0.00°），yaw 相对动作起始，四个头关节相对 HOME。

### 高度缩放

人的深蹲把骨盆压下去约 0.4 m，鸭子最多只能降 15 mm。默认 `height_scale = 0.035`，正好把一次完整深蹲落在鸭子极限内。

## 三、完整流水线

```bash
# 1) 重定向：人体关节位置 → Tremendous CSV
uv run python tools/retarget_human.py \
    --joints my_motion.npy --joint-names my_motion.joints.json \
    --out motion.csv

# 2) 批量：一个目录 → 一堆 CSV + 注册片段
uv run python tools/make_motion_library.py \
    --src motions/ --out <repo>/src/mjlab_microduck/tasks/motion_data \
    --register          # 自动把 DataMotion 行写进 expressive_motions.py

# 3) 训练（每个动作一个任务）
uv run list-envs                                       # 确认新任务在列表里
uv run train Mjlab-Expressive-MyMotion-MicroDuck --env.scene.num-envs 64 --agent.max_iterations 5   # 冒烟
uv run train Mjlab-Expressive-MyMotion-MicroDuck --env.scene.num-envs 4096 --agent.max_iterations 7000

# 4) 导出 ONNX（归一化会被烤进图里）
uv run scripts/export.py Mjlab-Expressive-MyMotion-MicroDuck \
    --checkpoint-file logs/rsl_rl/<experiment>/<run>/model_7000.pt

# 5) 装到机器人
sudo robotctl policy add my-motion <user>/microduck-my-motion
robotctl robot do my-motion
```

### 输入格式

`retarget_human.py` 接受：

| 格式 | 内容 |
|---|---|
| `.npy` | `(N, J, 3)` 关节位置；旁边放 `<name>.joints.json`（`{"joint_names": [...], "fps": 30}`） |
| `.npz` | 键 `joints` / `joint_names` / `fps` |
| `.json` | `{"joints": [...], "joint_names": [...], "fps": ...}` |
| `.csv` | 每行 J×3 个数 |

它认识的关节名（大小写不敏感）：

```
pelvis     pelvis | root | hips | hip
head       head
neck       neck | spine | base_of_spine | spine1
l_shoulder left_shoulder | l_shoulder | shoulder_l
r_shoulder right_shoulder | r_shoulder | shoulder_r
l_foot     left_foot | l_foot | foot_l | left_ankle | l_ankle
r_foot     right_foot | r_foot | foot_r | right_ankle | r_ankle
l_ear      left_ear | l_ear | ear_l      （可选，用来读头部侧倾）
r_ear      right_ear | r_ear | ear_r
```

**没有耳朵也能跑**，只是读不出头部 roll。

## 四、"堆起来"怎么做

三个层级，从简单到复杂：

### 1. 一个动作一个策略（上游的做法）

每个动作 = 一个 `DataMotion` = 一个任务 = 一个 ONNX = 机器人上的一个技能。

```bash
sudo robotctl policy add my-motion <user>/microduck-my-motion
robotctl robot do my-motion
sudo robotctl pad bind x my-motion        # 绑到手柄 X 键
```

真机有 7 个槽位（walk / stand / sitstand / ground_pick / kick_left / kick_right / roulade），技能是槽位之外、随时可触发的一次性动作。

### 2. 节目单：一个策略 + 时间轴

`microduck_challenges` 的 `got_a_talent` 挑战就是这个：策略只管执行，**节奏由 `timeline.json` 给**（关键帧：什么时候坐下、什么时候转头、什么角度）。多个动作串起来演成一段。

### 3. 一个策略管所有动作

上游的 expressive 任务**做不到**，因为策略看不见参考通道（观测里只有相位，看不出是哪个动作），所以每个动作必须一个策略。

要一个策略管全部，就得往空指令槽位里塞"动作身份"（比如 `body[0:2]` 放一个 one-hot 编码），或者把参考通道本身加进观测 —— 但那样就**破坏了 61 维契约**，真机运行时没法和走路/站立策略热切换了。

**所以除非必要，走 1 或 2。**

## 五、动作库从哪来（许可很重要）

| 数据集 | 内容 | 许可 | 能不能公开分享重定向后的数据 |
|---|---|---|---|
| **AMASS** | 40+ 小时动捕，11k+ 动作，SMPL/SMPL-X | MPI 学术许可，**非商用、禁止再分发、需注册** | ❌ |
| HumanML3D / BABEL / Motion-X | 基于 AMASS | 同上 | ❌ |
| **OpenCap** | 100+ 人的手机拍摄动作，CC BY 4.0，有开源处理管线 | **CC BY 4.0** | ✅ |
| CMU Graphics Lab Motion Capture | 大量 BVH 动捕 | 免费，无限制 | ✅ |
| LAFAN1 | Ubisoft 的 BVH 动作库 | 研究用 | ⚠️ |
| 文本生成动作（MDM 等） | 模型生成 | 看模型 | ✅ |
| **自己录** | 用 OpenCap 那套手机管线 | 你自己的 | ✅ |

**关键点**：AMASS 系的"衍生作品不继承许可"。就算你重定向过、再加工过，**公开分享仍然受限**（有 HF 上的资产许可清单明确写了这一点："Private hosting does not itself establish permission"）。

**如果朋友打算把动作库公开分享，AMASS 这条路走不通。** 干净的替代：

- **OpenCap**（CC BY 4.0）：而且它的**处理管线本身是开源的**（手机视频 → 3D 关节位置），所以可以自己拍人体动作，许可干净
- **CMU Mocap**（BVH，免费无限制）
- **文本生成动作**：无 mocap 授权问题

## 六、范围：上半身 vs 全身

这是**最难的一个决定**，差别很大。

### 上半身 / 表达性（脚不动）—— 好做

上游的 `expressive-motions` 分支就是这条路：**脚踩在原地不动，只有躯干和头在动**。重定向就是**纯旋转映射**，没有 IK、没有缩放、没有接触检测。

| 步骤 | 难度 |
|---|---|
| 躯干朝向 → roll/pitch/yaw | 简单 |
| 头部朝向 → 4 个关节角 | 中（数值 IK，本仓库已解决） |
| 骨盆高度 → dz | 简单（缩放） |
| 脚 | 不用管 |

**这是本仓库的 retargeter 实现的范围。**

### 全身 / 带脚步 —— 难一个数量级

`dance-steps` 分支做的是这个：CSV 里还要有左右脚的三维位置、接触调度（1=着地）、根节点 xy。

难点：

1. **空间缩放**：人腿 85 cm，鸭子腿约 7 cm —— 差 12 倍
2. **时间缩放**：不能简单按比例。**双足机器人用弗劳德相似性**：时间按 √长度缩放。长度比 0.147 → 时间比 √0.147 ≈ 0.38。**所以人 1.4 m/s 的步速，映射过去不是 0.11 m/s，而是 0.53 m/s** —— 也就是说人走路映射给鸭子会变成"慢跑"
3. **接触检测**：从人脚的高度/速度判着地/腾空
4. **可行性过滤**：人有的动作鸭子根本做不了（深蹲、跑跳、盘腿坐）

**而且**：上游明明试过脚步，最后还是**优先做脚不动的表达性动作**（`tremendous_planted.csv`），脚步版本放在另一个分支。这是个信号。

**建议**：先做表达性，跑通"人体动作 → 训练 → 部署 → 叠技能"的完整闭环，再考虑全身。

## 八、上游还留了什么坑

上游 `AGENTS.md` 记的教训，对这条路线同样适用：

- **奖励符号约定**：搞反过四次环境。万能检查：**wandb 里每个 `Episode_Reward/<penalty>` 必须 ≤ 0**
- **远偏的窄高斯核没梯度**：上游 v3 那一版，1029 次跑都把 `head_pitch` 停在 2.3 rad 外、从不往右倾 —— 因为误差太大时高斯核给不出梯度。解法是给头关节和躯干滚转加**线性偏离代价**（超出自由带的每弧度）
- **`dz` 只能到 −22 mm**，不是 −15 mm；过深会被关节限位卡住
- **`foot_slip` 权重 −0.1 而不是 −1.0**：−1.0 对这个机器人太限制转向
- **动作超时**：v3 用了 8 rad/s
- **最好的 checkpoint 经常不是最后一个**：要每个都打分
